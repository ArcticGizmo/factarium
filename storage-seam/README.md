# storage-seam — the swappable substrate, made concrete

A ~6-method interface every part of the system talks to, so the storage engine is
a one-line config change — the same "put it behind a seam" move used for data
sources. Proves the claim in [`../duckdb-vs-postgres.md`](../duckdb-vs-postgres.md)
that supporting **DuckDB or Postgres** is both possible and cheap.

```
storage-seam/
├── storage/
│   ├── engine.py         # StorageEngine ABC + RawRecord/SyncCursor  (the contract)
│   ├── duckdb_store.py   # real, runnable adapter (the default)
│   ├── postgres_store.py # STUB — same signatures, dialect diffs marked in comments
│   └── __init__.py       # get_store("duckdb" | "postgres")  <- the one knob
└── demo.py               # collect -> aggregate -> shape -> render, through the seam
```

## Run it

```bash
pip install duckdb
python demo.py
```

## The contract (all four verbs need only this)

| Method | Verb | Purpose |
|---|---|---|
| `land(records)` | collect | idempotent upsert of raw facts into the landing zone |
| `execute(sql)` | aggregate | run a re-runnable transform (raw → core) |
| `query(sql)` | shape / render | read a metric out as `list[dict]` |
| `get_cursor` / `set_cursor` | collect | incremental-sync watermark bookkeeping |
| `json_field(col, path)` | aggregate | dialect-specific JSON extraction, confined here |
| `initialize` / `close` | lifecycle | create landing tables; ctx-manager friendly |

The rest of the app imports `StorageEngine` and **never** imports `duckdb` or
`psycopg`. That is the whole trick.

## Where the two engines actually diverge (the "not free" part)

The stub marks these explicitly so the cost is visible, not hidden:

1. **Param placeholder** — DuckDB `?` vs psycopg `%s` (`paramstyle`).
2. **JSON type + cast** — DuckDB `JSON` / `CAST(? AS JSON)` vs Postgres `JSONB` /
   `%s::jsonb`.
3. **JSON path extraction** — DuckDB has a single dotted-path function
   (`json_extract_string(col,'$.a.b')`); Postgres chains `->` then `->>`. Both are
   generated by `json_field()`, so transform SQL stays identical.

Everything else — table shape, `ON CONFLICT DO UPDATE`, `now()`, standard
`SELECT/GROUP BY` — is the same. That's why the seam is thin.

## How this protects the scaling story

`demo.py` changes engine by editing one string: `get_store("duckdb", …)` →
`get_store("postgres", …)`. Nothing in the collect/transform/metric code moves.
So "switch to Postgres when a scale signal fires" is a config change, and the
federation escape hatch (point at an external aggregator as a new *source*) is the
same idea applied one layer up.

> Not yet in this spike: keeping the transform layer in **dbt** (adapters for both
> engines) so even the `CREATE TABLE core_… AS SELECT` step is portable for free.
> That's the recommended next layer — see the parent docs.
